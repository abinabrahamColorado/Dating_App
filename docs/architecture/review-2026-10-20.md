# Architecture review and gap analysis — 20 October 2026

Scope: M0 main `16676f3`, M1 PR #3 `3cc38d7`, source review and current local tests.
Authoritative design: unchanged 67-page architecture v0.2 PDF, P4–P26/P29–P32.
The full text/diagrams were read in this project conversation; source hashes were
reverified during this audit. Original and repository PDF SHA256:
`C4C27EC3560CEE9855D4129E06769E10330E87E0DFF86935D4206740C77DD4A0`.

**Assessment:** retain the modular monolith and current stack. The strongest
design choices are explicit bilateral boundaries, independent account/intent/nearby
states, no precise member location in MVP, a transactional capacity model, privacy
separation, and outcomes with missingness. Most of the introduction-to-meeting
system is still design, not implemented behavior. M1 is a synthetic local build;
it must not be promoted to live enrollment on the strength of passing tests.

Severity is the consequence **if exposed in a live product**: Critical = potential
safety/privacy violation; High = broken authority/durability or release blocker;
Medium = maintainability/operations weakness. “Missing” future scope is not a
claim that existing users have been harmed. Recommendations are proposed unless
explicitly marked implemented. Ordinary fixes are authorized; product changes,
production deployment, irreversible migrations and PR merges require approval.

## Review register

### G01 — Module and process boundaries (Medium)

- **Current/evidence:** core is pure policy; DB owns SQL; web handles transport.
  `apps/worker/src/main.ts` imports `apps/web/server/mail.ts`, which initializes a
  store with identity/app/ops pools and encryption keys.
- **Problem/improvement:** shared adapter placement widens worker credentials and
  reverses dependency direction. Extract an auth-mail application service with
  injected identity repository/transport before adding product delivery jobs.
- **Alternatives/tradeoffs:** retain import briefly for M1 versus a small shared
  package; microservices add failure/operational boundaries without present evidence.
  A modular monolith can still use a separately credentialed safety process.
- **Migration/verification/approval:** no data rewrite; change worker wiring and
  configuration, deny unused-role access in integration tests. Routine refactor
  within M2/M3; any new production deployment topology needs review.

### G02 — Authentication/session lifecycle (High before live enrollment)

- **Current:** browser-bound expiring links, hashed sessions, passkeys with user
  verification, recent auth for deletion/staff changes; `server/passkeys.ts`,
  `server/api.ts`, `db/accounts.ts`.
- **Problem/improvement:** no passkey removal/recovery or tested key rotation;
  session authority is loaded before consequential writes. Define revocation
  linearization and recheck current session/policy in the transaction protocol.
- **Alternatives/tradeoffs:** opaque DB sessions remain easier to revoke than
  stateless bearer claims; managed auth could reduce maintenance but introduces
  vendor/data-flow decisions. Cross-schema lock order must avoid deadlocks.
- **Migration/verification/approval:** additive credential metadata and lifecycle
  endpoints; race signout/deletion versus mutation, challenge replay and revoked
  credentials. Existing denial rules are approved; provider/recovery policy needs
  founder review. Do not infer identity verification from DOB entry.

### G03 — Object authorization and staff revocation (Critical release gate)

- **Current:** owner/role checks, audited pending-media reads, no self-moderation;
  `photoAccess`, `moderate`, `staffRoles`. Schema grants are real, but all web keys
  share a process.
- **Problem/improvement:** moderator eligibility is checked outside its mutation
  transaction; photo access check commits before object retrieval. Define a final
  disclosure authorization point and transactional revocation protocol; separate
  case-access credentials before safety narratives exist.
- **Alternatives/tradeoffs:** long-held locks around I/O simplify ordering but hurt
  availability; short transactions with version checks require a precise final
  read/send boundary. Already transmitted bytes cannot be recalled.
- **Migration/verification/approval:** versioned authority projections/roles, no
  permission broadening; deterministic restriction/read and restriction/moderate
  races, deny on authority-store outage. Routine implementation; production role
  topology and any exposure change need approval.

### G04 — Safety, blocks, reports, restrictions and appeals (Critical / M2)

- **Current:** safety schema/role exists; product tables/APIs do not. M1's RESTRICTED
  state denies restoration; EXIT can replace that state (`core/accounts.ts`).
- **Problem/improvement:** account lifecycle must not become the sole record of
  enforcement. Create independent durable enforcement, unordered deny pairs and
  restricted case narratives. Report without block, block without report; reporting
  and appeals remain reachable after exit/unmatch and subject deletion.
- **Alternatives/tradeoffs:** a single state enum is simpler but loses concurrent
  restriction reasons. Append-only case events plus a narrow serving projection
  add joins but preserve history and need-to-know access.
- **Migration/verification/approval:** additive safety/app schemas, constrained
  role functions and audits; deny precedence races, staff assignment matrix,
  reporter confidentiality and report-after-removal tests. Requirements approved;
  staffing, escalation promises and retained legal-hold policy need review.

### G05 — Reciprocal eligibility and population coverage (High / M3)

- **Current:** `boundariesAllow` tests bilateral stated preferences only; all other
  gates/feasibility are absent. Pilot vocabulary/catchment remain provisional.
- **Problem/improvement:** compose adult eligibility, state, enforcement, closed
  pairs, consent, media readiness, common time and public-venue travel feasibility
  into one explainable server gate. Unknown hard-boundary values must fail closed.
- **Alternatives/tradeoffs:** loosening constraints to fill cards violates the spec;
  narrower recruitment or honest empty states preserve consent but reduce coverage.
  Optional availability must not accidentally exclude everyone with flexible hours.
- **Migration/verification/approval:** immutable input versions and eligible-edge
  snapshots; synthetic sparse/dense/mixed-boundary graphs, timezone/DST/travel
  edges and coverage by operational reason. Approved gates; vocabulary, age-out
  policy or catchment expansion require product approval.

### G06 — Allocation, capacity and irreversible pair decisions (Critical / M3)

- **Current:** capacity helper/config only; no reservation/decision/pair tables.
- **Problem/improvement:** lock member rows in stable ID order; create both holds,
  pair opportunity and outbox atomically. Accept the reservation already held,
  without counting its last slot twice. Close/release exactly once; retain pass,
  expiry and ended-connection distinctions; never disclose one-sided choices.
- **Alternatives/tradeoffs:** per-member counters without a ledger hide leaks;
  cache locks add split-brain risk. Start with a deterministic feasible-edge
  heuristic and exact small-graph comparator, not ML or a distributed allocator.
- **Migration/verification/approval:** additive ledger/reservation/pair tables with
  unique constraints/versioning; multi-connection contention, deadlocks/retries,
  last-slot acceptance, block-versus-accept, duplicate expiry and closed-pair
  resurfacing tests. Approved architecture; heuristic weight changes are recorded
  hypotheses, consequential allocation policy changes need approval.

### G07 — Retry and delivery correctness (High; focused M1 fix implemented)

- **Current problem:** one failed auth email rolled back a ten-message transaction,
  including `sent_at` for earlier successful SMTP sends.
- **Improvement implemented:** migration 0004 adds due time; each message locks and
  commits separately. Failures persist attempt count/backoff; exhausted, consumed,
  expired and not-yet-due rows are excluded. Config owns limits; adapter bounds
  connection/greeting/socket waits and logs counts without payloads.
- **Alternatives/tradeoffs:** full claim/lease outbox avoids network-held locks but
  adds fencing/recovery complexity. M1 retains a bounded per-message lock; future
  product outbox needs independent delivery authorization, idempotent effects and
  operational expiry. SMTP cannot guarantee exactly-once after an ambiguous send.
- **Migration/verification/approval:** additive local/test migration, no secret/data
  export; four real PostgreSQL regression tests include deferred COMMIT failure
  after SMTP acceptance and concurrent senders. Merge requires explicit approval.
  Whole-process crash/slow-trickle transport testing remains a release test gap.

### G08 — Client idempotency and recovery (High before plans/payments)

- **Current:** server mutation receipts bind payload/key; browser `components/client.tsx`
  generates a new key every invocation. `useMember.refresh` catches errors internally.
- **Problem/improvement:** retries after lost responses can become new operations;
  retain command key/payload until reconciled. Refresh failures must not advance a
  dependent onboarding step. Initialize settings from persisted values.
- **Alternatives/tradeoffs:** disabling a button prevents double-clicks, not network
  ambiguity; persistent pending commands need expiry and cross-tab reconciliation.
- **Migration/verification/approval:** no mandatory DB rewrite; explicit typed
  success/conflict/unknown outcomes. E2E lose response after commit, retry upload,
  stale tab and interrupted refresh. Routine M1/M3 correction; no new product policy.

### G09 — Secure media and storage consistency (High release gate)

- **Current:** bounded decode/re-encode strips metadata; private encrypted S3;
  DB cap under member lock. API compensates failed upload by deleting written object.
- **Problem/improvement:** a DB commit may succeed despite a lost acknowledgement;
  blind compensation can delete an object whose metadata committed. Use upload
  intent/reconciliation with durable ownership and status; ambiguous outcomes must
  remain pending for reconciliation, not destructive cleanup. Add orphan retention.
- **Alternatives/tradeoffs:** storing bytes in Postgres simplifies atomicity but
  increases DB cost; staged objects add a state machine but permit bounded cleanup.
- **Migration/verification/approval:** additive upload-intent/status records and
  reconciler; inject storage failure, ambiguous commit, crash between systems and
  concurrent removal/review; verify no stale disclosure. Ordinary safe correction;
  new storage vendor/access policies need approval.

### G10 — Deletion, retention and restore (Critical live-pilot gate)

- **Current:** DELETE records intent, disables authority and revokes sessions;
  there is no erasure orchestrator. Runtime histories reject UPDATE/DELETE.
- **Problem/improvement:** use a narrowly privileged deletion role/orchestrator,
  tombstones outside the restore being applied, retryable store-specific receipts
  and a restore gate before serving. Preserve only scoped, reviewed safety holds.
  Do not weaken append-only runtime privileges to make erasure convenient.
- **Alternatives/tradeoffs:** crypto-erasure alone misses indexes, exports and
  metadata; direct deletion alone misses restored backups. Combine lifecycle
  controls with audited privileged deletion and snapshot lineage.
- **Migration/verification/approval:** additive job/tombstone/receipt schema and
  role grants; primary/media/export/cache scans, expired holds and restore drills.
  M5 retains this scope; no real users before it passes. Actual production deletion
  migrations, hold exceptions and retention/legal decisions require approval.

### G11 — Plans, messaging and notifications (Critical / M4)

- **Current:** not implemented. Only auth mail is live in local development.
- **Problem/improvement:** conversation membership and block checks on every read/
  write; plan revisions immutable; both confirm one version and venue validity
  under the same concurrency protocol. Notify via transactionally created opaque
  events and a fresh authorization check before delivery. Generic content only.
- **Alternatives/tradeoffs:** sockets may improve latency later; polling is simpler
  initially. Auto-booking increases vendor/cancellation complexity and is deferred.
- **Migration/verification/approval:** conversation/message/plan/confirmation/outbox
  tables; version-confirmation, venue closure, cancel/block/confirm and duplicate
  delivery races; no origin disclosure. Approved workflow; booking vendors and
  communication retention deviations require approval.

### G12 — Geospatial and Go authority (Critical / M6, flags off)

- **Current:** curated broad area IDs, static public reference centroids, GHOST only;
  event/Go/session processing absent. Public-area centroids are not member GPS.
- **Problem/improvement:** keep event tokens separate from plans; Stop increments
  epoch, revokes leases and cancels pending nearby disclosures/reservations.
  Existing mutual Go reuses held connection capacity. No member coordinates.
- **Alternatives/tradeoffs:** neighborhood GPS increases privacy/native complexity;
  event-bound and existing-match sessions offer a smaller measurable experiment.
- **Migration/verification/approval:** event consent/check-in/lease/epoch records;
  stale retries, authorization outage, stop-versus-deliver, restart and collusion
  probes; measure revocation acknowledgement. Prototype authorized after prior
  gates; real activation, stranger Go and any GPS work require explicit approval.

### G13 — Learning, fairness and observability (High / M3–M5)

- **Current:** learning schema/config and documented exposure contract; no model or
  datasets. Request IDs and a few structured operational events; no alerting/SLOs.
- **Problem/improvement:** log selection snapshots, feasible-set identity/size and
  conditional `q`; distinguish operator choices with unknown propensity. Separate
  experience, logistics, integrity and safety; cohort metrics include missingness.
  Add aggregate queue-age, delivery-failure and invariant-failure alerts/runbooks.
- **Alternatives/tradeoffs:** raw event warehouses are easy but overcollect; minimal
  aggregates limit retrospective analysis. Propensity logging alone does not remove
  marketplace interference or make observational outcomes causal.
- **Migration/verification/approval:** append-only minimized events/export lineage;
  forbidden-field scans, denominator fixtures and alert drills. No chat/report text,
  location or inferred sensitive traits in learning/logs. New data collection or
  serving ML requires a separate approved design.

### G14 — Accessibility, moderation UX and error handling (High for access; Medium for polish)

- **Current:** real backend-driven mobile pages, CSS tokens, axe on public/member/ops
  screens and scripted keyboard/mobile coverage. Moderation queue is capped at 25
  without pagination; onboarding latency is scripted, not a human study.
- **Problem/improvement:** manual assistive-tech testing, accessible error/focus
  recovery, clearly persisted controls, queue pagination and operational state
  explanations. Avoid making completion contingent on fast photo moderation.
- **Alternatives/tradeoffs:** a component library is optional; maintaining small
  native controls avoids a redesign but needs documented usage patterns.
- **Migration/verification/approval:** cursor API for queue, no sensitive extra
  fields; screen reader/zoom/reduced motion/slow-network and long-queue tests.
  Routine accessibility fixes authorized; user-study recruitment needs approval.

### G15 — Supply chain, abuse, cost and release operations (High release gate)

- **Current:** pinned lockfile/release-age rules, Windows and Linux CI, no secrets in
  tracked files, global/email request budgets; no dedicated secret-scanning workflow,
  public deployment, load model, incident drills or real provider contracts.
- **Problem/improvement:** add automated secret/dependency review, pin CI action
  revisions, budget discovery/upload/anonymous traffic and request-body time,
  scope storage credentials, rotate keys, rehearse backups/kill switches. Measure
  DB lock waits, candidate edges, image memory and operator minutes before scaling.
- **Alternatives/tradeoffs:** managed services reduce maintenance but add cost and
  data processors; microservices/Rust should follow measured bottlenecks. Caching
  authorization to save latency risks stale permission. Rate limits need fairness
  and recovery when global budgets are exhausted.
- **Migration/verification/approval:** additive operational configs and indexes;
  clean-clone Windows/Linux checks, dependency audit, threat scans, load profile,
  recovery exercise and per-member cost estimate. Vendor spend, production topology,
  deployment and any irreversible migration require explicit approval.

## Contradictions and proposed amendments

1. **Roadmap numbering:** the new directive calls deletion M6 and Go M7; existing
   prompts put deletion in M5, Go in M6, hardening in M7. Keep IDs and use the
   [crosswalk](../product/roadmap.md); do not postpone deletion. Hardening is a
   continuous gate, not work postponed until after a live Go event.
2. **Safety state versus account state:** preserve independent enforcement through
   exit/deletion/appeal. M1 state alone is insufficient for M2; G04 records the plan.
3. **No precise location versus public centroids:** the MVP prohibition applies to
   member coordinates/history; curated public-area reference geometry is a separate
   field class. Do not convert area selection into inferred member position.
4. **Append-only history versus erasure:** application immutability is not permanent
   retention; explicit privileged erasure and reviewed case holds are required.
5. **Finite supply and permanent closure:** refusing to recycle declined pairs may
   exhaust a small pool. Show honest emptiness and test coverage; do not silently
   relax explicit boundaries or replenish with ineligible profiles.
6. **Production aspirations versus evidence:** 41 automated tests after this slice
   do not establish hundreds-of-thousands scale, independent security review,
   human usability, staffed safety or product-market fit. No new language is justified.

These are implementation clarifications/proposals. The PDF and original prompts
remain unchanged. DEC-029–031 record authority, the focused repair and reconciliation.
